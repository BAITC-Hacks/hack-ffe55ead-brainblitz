# Аким на 5 часов

Учебный AI-симулятор управления городским бюджетом: **100 условных единиц → 5 решений → последствия для районов → объяснение AI → повторная попытка**.

Пользователь распределяет ограниченный бюджет между городскими инициативами и получает **Astana Quality of Life Score** с объяснением сильных сторон, рисков и компромиссов своего сценария.

**Статус:** реализованы математический backend, полный датасет, серверная валидация, существующий frontend и `POST /api/analyze` с адаптером OpenAI Responses API. Проверки после интеграции: **256 Python-тестов и 12 браузерных тестов прошли**. Математика, датасет и `static/` не изменены. **Живые AI-разборы A/B пока не подтверждены:** для их проверки нужно задать действующий `AI_API_KEY` и доступный `AI_MODEL` в окружении сервера.

## Проблема и пользователь

Транспорт, озеленение, социальная инфраструктура, безопасность и городские сервисы конкурируют за один бюджет. Улучшение среднего показателя города может оставлять критические проблемы отдельных районов нерешёнными.

Основная учебная аудитория — студенты и слушатели программ городского управления, урбанистики и экономики. Преподаватель может использовать симулятор для обсуждения распределения ресурсов; управленец или аналитик — участвовать в таком упражнении.

Цель — научиться объяснять последствия выбора. Пользователь меняет решение, сравнивает результат и разбирает, кому помогло изменение и какая проблема осталась.

**Границы модели:** данные синтетические, стоимости и эффекты условные. Astana Quality of Life Score здесь — учебный индекс, а не официальный показатель или прогноз развития Астаны. Образовательная эффективность пока не проверена на пользователях.

## Основной сценарий

1. Увидеть исходные показатели пяти районов и базовый Score **52,56**.
2. Выбрать ровно пять мероприятий и районы для локальных мер.
3. Проверить расход и остаток общего бюджета **100**.
4. Получить понятную ошибку, если набор нарушает правила.
5. Рассчитать итоговый Score, изменения по районам и критические показатели.
6. Получить AI-разбор сильных сторон, рисков и основного компромисса.
7. Изменить решение и повторить расчёт.

## Данные и правила

Источник модели — предоставленный для задачи документ «Датасет районов», полный набор чисел зафиксирован в спецификации и API-контракте. Машиночитаемая версия `city-v1` находится в [data/districts.json](data/districts.json) и [data/measures.json](data/measures.json). Сервер проверяет их при старте и использует один неизменяемый снимок данных.

| Параметр | Значение |
| --- | --- |
| Бюджет | 100 условных единиц для всех пользователей |
| Районы | Есиль, Алматы, Сарыарка, Байконур, Нура |
| Направления | Транспорт, экология/озеленение, соцсфера, безопасность, сервисы |
| Показатели | 10; каждый от 0 до 100, больше — лучше |
| Каталог | 14 мероприятий |
| Горизонт | 8 кварталов, два условных года |
| Число решений | Ровно 5 |
| Остаток бюджета | Допустим, бонуса к Score не даёт |

Правила MVP на основе исходного документа:

- Каждое мероприятие выбирается не более одного раза.
- Для меры типа «Район» обязателен один существующий район.
- Для меры типа «Город» район не указывается; эффект применяется ко всем пяти районам.
- Ровно одно мероприятие из каждого из пяти направлений.
- Порядок решений не влияет на результат.
- При любом нарушении Score не рассчитывается; сервер возвращает причину.

**Принятое допущение:** команда зафиксировала обязательный охват всех пяти направлений. Это более строгое правило, чем «не более двух мер на направление» в исходном документе. Для MVP используется только строгий вариант, без переключателя; demo-сценарии A/B ему соответствуют.

### Несовместимости и синергии

| Несовместимые меры | Ограничение |
| --- | --- |
| M1 и M3 | Нельзя выбирать вместе независимо от района |
| M4 и M7 | Нельзя размещать в одном районе |
| M5 и M13 | Нельзя размещать в одном районе |

| Пара с синергией | Фиксированный бонус |
| --- | --- |
| M1 + M2 | T1 +2 в районе M1 |
| M10 + M12 | B1 +2 в районе M10 |
| M5 + M6 | E2 +2 в районе M5 |

Бонусы синергий не масштабируются лагом. При правиле «по одному мероприятию на направление» пары M1+M2 и M5+M6 недоступны; M10+M12 остаётся допустимой.

## Расчёт Score

```text
realized_effect = full_effect × (8 − lag) / 8
new_indicator = clip(initial_indicator + sum(realized_effects) + synergies, 0, 100)
district_score = sum(weight × new_indicator)
city_average = sum(population_share × district_score)
critical_count = число пар «район × показатель» со значением строго меньше 40
Score = 0.7 × city_average + 0.3 × min(district_score) − critical_count
```

| Показатель | T1 | T2 | E1 | E2 | S1 | S2 | B1 | B2 | C1 | C2 |
| --- | --- | --- | --- | --- | --- | --- | --- | --- | --- | --- |
| Вес | 0.10 | 0.10 | 0.09 | 0.11 | 0.11 | 0.11 | 0.09 | 0.09 | 0.10 | 0.10 |

| Район | Доля населения | Исходная оценка |
| --- | --- | --- |
| Есиль | 0.27 | 62.99 |
| Алматы | 0.24 | 57.06 |
| Сарыарка | 0.20 | 54.65 |
| Байконур | 0.13 | 56.63 |
| Нура | 0.16 | 49.18 |

Базовое среднее — **56.8624**, слабейший район — **Нура**, критических показателей — **2**. Базовый Score: **52.55768**, в интерфейсе **52,56**.

Округление выполняется только для отображения. Значение ровно 40 не является критическим. Ограничение 0–100 применяется к показателям; дополнительное ограничение итогового Score исходной формулой не предусмотрено.

## Архитектура и роль AI

Стек backend: **Python, FastAPI, Pydantic**; frontend — HTML/CSS/JavaScript. Один сервер обслуживает API и существующий статический интерфейс. Для локального MVP не нужны база данных и авторизация.

```text
Браузер → серверная валидация → Python-расчёт → числовой результат
                                            ↓
                                  отдельный AI-разбор
```

**Python отвечает за числа:** бюджет, эффекты, лаги, синергии, конфликты и Score. Сервер получает ID решений и берёт стоимости и показатели из собственного датасета, не доверяя числам от браузера.

**AI отвечает за объяснение:** сильные стороны, сохраняющиеся проблемы, компромисс и один вопрос для следующей попытки. Он получает рассчитанные факты и не определяет итоговый балл. Числовые рекомендации допустимы только для альтернатив, заранее проверенных расчётным модулем.

Подключён один провайдер — **OpenAI Responses API** через асинхронный `httpx`, без отдельного SDK. Конкретный ID задаётся в `AI_MODEL`; модель по умолчанию не назначается. Используются Structured Outputs и `store=false`. Ответ проверяется по строгой схеме, длине и ссылкам на рассчитанные факты; эти проверки не гарантируют отсутствия смысловых ошибок. Ключ и модель не были предоставлены среде разработки, поэтому живой вызов ещё не проверен.

При timeout, отказе или некорректном ответе модели расчёт остаётся доступным. Интерфейс сообщает «AI-разбор недоступен». Детерминированная сводка или запись предыдущего разбора не выдаются за живой AI-ответ. После изменения решений старый результат помечается как устаревший; поздний AI-ответ не должен подменять новую попытку.

### API и состояние реализации

| Метод | Путь | Назначение | Статус |
| --- | --- | --- | --- |
| GET | `/api/config` | Бюджет, районы, каталог, правила и версия данных | Реализован |
| POST | `/api/simulate` | Валидация решений и расчёт без обращения к AI | Реализован |
| POST | `/api/analyze` | Повторная валидация и расчёт, затем AI-разбор | Реализован; живой доступ требует проверки |
| GET | `/health` | Проверка доступности приложения | Реализован |

Оба POST получают объект с единственным полем `selections`: список решений с `measure_id` и `district_id`; у городской меры `district_id` равен `null` или отсутствует. ID районов зафиксированы: `esil`, `almaty`, `saryarka`, `baikonur`, `nura`. Невалидный набор возвращает HTTP 422 с единственной ошибкой в `detail[0]`, без Score и обращения к AI. Дополнительные входные поля запрещены.

## Запуск и конфигурация

Нужен **Python 3.11 или новее**. Математический backend ранее проверен на Windows с CPython 3.12.14; исходные тесты перед AI-интеграцией повторены на macOS с CPython 3.14.4. Из корня репозитория в PowerShell:

```powershell
python -m venv .venv
.\.venv\Scripts\python.exe -m pip install -r requirements.txt
.\.venv\Scripts\python.exe -m pip check
.\.venv\Scripts\python.exe -m pytest -q
.\.venv\Scripts\python.exe -m uvicorn app.main:app --host 127.0.0.1 --port 8000
```

После старта откройте **`http://127.0.0.1:8000/`** для интерфейса, `http://127.0.0.1:8000/docs` для интерактивных запросов или `http://127.0.0.1:8000/api/config` для конфигурации. `/health` возвращает `{"status":"ok"}`. Установка из полного списка зафиксированных зависимостей `requirements.txt` повторена в отдельном чистом окружении `.venv-verify`; `pip check` не обнаружил конфликтов.

Результат `.venv/bin/python -m pytest -q` после интеграции — **256 passed, 1 warning in 1.21s**; `.venv/bin/python -m pip check` — **No broken requirements found**. Предупреждение Starlette относится к будущему переходу TestClient с `httpx` на `httpx2`. Исходный прогон дал 131 passed: сохранены 130 проверок, а единственное устаревшее ожидание 404 от `/api/analyze` заменено проверками реализованного маршрута в составе 126 новых AI-проверок. Допуск числовых эталонов — абсолютный `1e-8`.

AI-ключ не требуется для запуска приложения и расчётов. `/` и `/static/*` обслуживаются на том же origin, что и API. Интерфейс сначала показывает числа, затем запрашивает `/api/analyze`. Без настройки AI маршрут возвращает HTTP 200 с `status="unavailable"`, `unavailable_reason="not_configured"` и рассчитанными Score; интерфейс сохраняет числа.

| Переменная | Назначение |
| --- | --- |
| `AI_API_KEY` | Обязательный секретный ключ OpenAI, только на сервере |
| `AI_MODEL` | Обязательный точный ID доступной модели с Responses API и Structured Outputs; без значения по умолчанию |
| `AI_BASE_URL` | По умолчанию `https://api.openai.com/v1`; адаптер добавляет `/responses` |
| `AI_TIMEOUT_SECONDS` | Общий deadline, по умолчанию 12 секунд, без повторов |
| `AI_ENABLED` | По умолчанию `true`; `false` возвращает `disabled` |

Для macOS / Linux, bash или zsh:

```sh
python3 -m venv .venv
.venv/bin/python -m pip install -r requirements.txt
cp .env.example .env
```

Откройте `.env` в редакторе и заполните ключ и точный ID модели из выданного доступа. **`.env` автоматически не загружается.** В том же терминале:

```sh
set -a
source .env
set +a
.venv/bin/python -m uvicorn app.main:app --host 127.0.0.1 --port 8000
```

Для PowerShell используйте [инструкцию со скрытым вводом ключа](docs/ai.md#запуск-на-windows-powershell). Ключ не вставляйте в команду, prompt или Git. Бюджет, эффекты и веса остаются в данных. `.env` уже исключён из Git; `.env.example` не содержит секретов.

Если организаторы дали свой API-адрес, он должен поддерживать Responses API и Structured Outputs; одной совместимости с Chat Completions недостаточно. При отсутствии ключа/модели или неверной конфигурации `/api/analyze` возвращает `not_configured`. После изменения окружения перезапустите сервер. [Полная настройка и диагностика](docs/ai.md).

Проверки без платных запросов:

```sh
.venv/bin/python -m pytest -q tests/test_ai.py tests/test_analyze_api.py
.venv/bin/python -m pytest -q
.venv/bin/python -m pip check
```

AI-тесты подменяют транспорт провайдера. Браузерная команда `node tests/frontend.cjs` дала **12 passed**; все API в ней подменены. Нужны Playwright и Chromium; при внешней установке задайте `NODE_PATH`, для выбранного браузера — `BROWSER_PATH`.

Отдельно проверен настоящий интерфейс с Uvicorn, без `?demo=1` и подмены API: A показал **53,83**, B — **55,07**, оба стоимостью **83**; критических пар стало 1 вместо 2, S1 Нуры — 48 вместо 38, S2 остался 35. Статус AI `not_configured` сохранил числа. Живых вызовов модели было **0**, её ID и задержка пока не определены. Для живой приёмки выполните A/B после настройки ключа и модели по [чеклисту](docs/ai.md#живая-приёмка-ab).

Стоимости исходных данных сохранены; подробности — в [документации backend](docs/backend.md#проверки-и-известное-расхождение-в-документах).

### Проверено backend-тестами

- Базовый расчёт и сценарии A/B с допуском для вычислений с плавающей точкой.
- Бюджет ровно 100 и больше 100; неверное количество решений; повторы и направления.
- Корректность районов и различие локальных и городских мер.
- Все несовместимости, лаги и фиксированные синергии.
- Отрицательный эффект M11, ограничение показателей 0–100, границу строго меньше 40.
- Независимость от порядка мер и отсутствие накопления эффектов между запросами.
- Точный HTTP-контракт, порядок стадий проверки и ошибки 422.
- Проверка целостности данных при запуске и остановка запуска при их повреждении.

Проверки AI вынесены в `tests/test_ai.py` и `tests/test_analyze_api.py`: строгий ответ и ссылки, отсутствие вызова при 422, отказ, timeout и сохранение числового результата при недоступности. Они не обращаются к платному API. Живые разборы A/B остаются обязательной отдельной приёмкой.

## Demo на 60 секунд

Это сценарий приёмки после задания ключа и доступной модели. Числовые A/B доступны через интерфейс и API; пока живая проверка AI не выполнена, успешное полное demo не считается подтверждённым.

| Время | Действие |
| --- | --- |
| 0–10 сек. | Показать исходные районы и бюджет; объяснить учебную задачу |
| 10–25 сек. | Рассчитать A: расходы 83, Score 53,83, два критических показателя |
| 25–35 сек. | Показать AI-разбор и перенести только школу M7 из Есиля в Нуру |
| 35–50 сек. | Рассчитать B: расходы остаются 83, Score становится 55,07, критический показатель один |
| 50–60 сек. | Объяснить компромисс и предложить следующую попытку |

На случай сбоя подготовить локальный запуск и явно обозначенную запись успешного AI-разбора. Числовой результат должен появляться независимо от скорости AI.

## Командная работа и готовность

| Роль | Зона ответственности |
| --- | --- |
| Frontend / UX | `static/`, выбор решений, бюджет, ошибки и отображение результата |
| Backend / AI | `app/`, валидация, расчёт, API, AI-разбор и обработка сбоев |
| Data / QA / Docs / Pitch | `data/`, `tests/`, `examples/`, окружение, README, запуск и demo |

| Рубеж | Проверяемый результат |
| --- | --- |
| 1 час | Данные и API-контракт согласованы; модель отдельно считает эталоны |
| 2 часа | Полный пользовательский путь без AI, включая ошибки и повторный расчёт |
| 3 часа | Рабочий AI-разбор и обработка недоступности API |
| 4 часа | Проверены запуск, тесты и demo; новые функции больше не добавляются |
| 5 часов | Зафиксирована и сдана проверенная версия |

## После хакатона

Следующий шаг — пилотное занятие с преподавателем и небольшой группой: проверить, помогают ли повторная попытка и AI-разбор лучше объяснять последствия решений. После подтверждения пользы — задания преподавателя, история попыток и новые учебные сценарии. Эти возможности пока не реализованы.
