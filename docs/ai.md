# AI-разбор: OpenAI Responses API

Реализован `POST /api/analyze` по контракту `2.0`. Провайдер один — OpenAI; NVIDIA и автоматическое переключение не подключены. Запрос выполняется асинхронно через уже используемый `httpx`, без нового SDK. Числа считает существующая функция `simulate`; AI объясняет её результат.

**Живая интеграция подтверждена для A/B:** настоящий интерфейс без `?demo=1` получил разборы от `gpt-4.1` через `https://api.openai.com/v1`. Оба ответа — HTTP 200, `status=ok`; время `/api/analyze` — **3,57 с для A и 2,62 с для B**. Ключевые выводы проверены вручную. В коде по-прежнему нет модели по умолчанию: задайте `AI_MODEL` в окружении своего backend. Эти два результата не гарантируют качество всех будущих ответов.

Документы [backend](backend.md) и [frontend](frontend.md) описывают предыдущие этапы. Их упоминания отсутствующего `/api/analyze` относятся к состоянию до этой интеграции. Актуальная настройка AI приведена здесь и в [README](../README.md).

## Как работает запрос

1. Браузер сначала вызывает `/api/simulate` и показывает числа.
2. Затем отправляет в `/api/analyze` тот же объект с единственным полем `selections`.
3. Сервер вызывает `simulate(payload.selections, request.app.state.config)` заново. Невалидный набор получает ту же первую ошибку 422; запрос к OpenAI не выполняется.
4. Адаптер отправляет рассчитанный `SimulationResult`, названия мер и показателей из серверного каталога и системный промпт `app/prompts/analyst.txt` в `POST {AI_BASE_URL}/responses`.
5. Ответ запрашивается через `text.format` с `type=json_schema`, строгой схемой и `store=false`. Сервер проверяет JSON, Pydantic-схему, ограничения текста и все `evidence_paths`.
6. Сервер самостоятельно собирает `AnalysisResult`: версии, нормализованные решения, исходный и итоговый Score, статус и сообщение не берутся из ответа модели.

Клиент провайдера создаётся на время работы приложения и закрывается при завершении. Один разбор делает не более одного HTTP-запроса, без автоматических повторов. Общий deadline по умолчанию — 12 секунд, включая ожидание полного ответа; медленный AI не блокирует `/health` и расчёт. Для `asyncio.timeout` нужен **Python 3.11 или новее**.

## Настройки

| Переменная | Значение и поведение |
| --- | --- |
| `AI_ENABLED` | По умолчанию `true`; `false` отключает обращения и возвращает `disabled` |
| `AI_API_KEY` | Обязательный ключ при включённом AI, только в окружении backend |
| `AI_MODEL` | Обязательный точный ID модели, доступной команде; значения по умолчанию нет |
| `AI_BASE_URL` | По умолчанию `https://api.openai.com/v1`; укажите базовый путь без `/responses` |
| `AI_TIMEOUT_SECONDS` | Положительное конечное число секунд, по умолчанию `12` |

При отсутствии обязательных настроек или некорректной конфигурации включённый AI возвращает `not_configured`. В адресе API разрешён HTTPS без логина, пароля, query-параметров и fragment; ключ передаётся только заголовком, не в URL. Приложение при этом запускается, а `/health`, `/api/config`, `/api/simulate` и интерфейс продолжают работать. Настройки читаются при старте: после изменения окружения перезапустите сервер.

Используйте точный ID из выданного доступа и проверьте, что модель поддерживает **Responses API и Structured Outputs**. Само наличие ключа не доказывает доступ к выбранной модели. Если организаторы дали свой адрес, он должен поддерживать `POST /responses` и `text.format.json_schema`; совместимости только с `/chat/completions` недостаточно. Не добавляйте переключение API и не подставляйте случайный model ID для обхода ошибки конфигурации.

Проверенная при приёмке настройка — `AI_MODEL=gpt-4.1`, `AI_BASE_URL=https://api.openai.com/v1`, `AI_TIMEOUT_SECONDS=12`, `AI_ENABLED=true`. Доступ к модели подтверждён для выданного команде ключа; это не подтверждение доступа у других аккаунтов. Официальная документация: [GPT-4.1](https://developers.openai.com/api/docs/models/gpt-4.1), [Responses API](https://developers.openai.com/api/docs/guides/migrate-to-responses), [Structured Outputs](https://developers.openai.com/api/docs/guides/structured-outputs). `store=false` отключает хранение ответа для последующего получения через Responses API; это не обещание полного отсутствия обработки или хранения данных провайдером по его правилам.

## Запуск на macOS / Linux, bash или zsh

Из корня репозитория:

```sh
python3 -m venv .venv
.venv/bin/python -m pip install -r requirements.txt
cp .env.example .env
```

Откройте локальный `.env` в редакторе, заполните `AI_API_KEY` и `AI_MODEL`. При необходимости измените `AI_BASE_URL`. Значения с пробелами или специальными символами должны быть корректно заключены в кавычки shell. `.env` исключён из Git. Загружайте только свой доверенный файл: `source` выполняет его как shell-код.

**Файл `.env` не загружается автоматически.** В том же терминале, из которого запускаете сервер:

```sh
set -a
source .env
set +a
.venv/bin/python -m uvicorn app.main:app --host 127.0.0.1 --port 8000
```

Так ключ не вводится в строке команды и не попадает в историю shell. Не выводите содержимое `.env` или окружения для диагностики. Для проверки без AI выставьте `AI_ENABLED=false` в файле, снова загрузите его и перезапустите сервер.

## Запуск на Windows, PowerShell

Из корня репозитория создайте окружение и установите зависимости:

```powershell
python -m venv .venv
.\.venv\Scripts\python.exe -m pip install -r requirements.txt
```

Задайте несекретные настройки в текущем терминале и введите ключ скрытым вводом. Вместо текста в `AI_MODEL` укажите ID из выданного доступа. Этот пример не читает `.env`:

```powershell
$env:AI_ENABLED = 'true'
$env:AI_MODEL = 'ID_МОДЕЛИ_ИЗ_ВАШЕГО_ДОСТУПА'
$env:AI_BASE_URL = 'https://api.openai.com/v1'
$env:AI_TIMEOUT_SECONDS = '12'
$aiSecret = Read-Host 'OpenAI API key' -AsSecureString
$aiKeyPointer = [Runtime.InteropServices.Marshal]::SecureStringToBSTR($aiSecret)
try {
    $env:AI_API_KEY = [Runtime.InteropServices.Marshal]::PtrToStringBSTR($aiKeyPointer)
} finally {
    [Runtime.InteropServices.Marshal]::ZeroFreeBSTR($aiKeyPointer)
    $aiSecret.Dispose()
    Remove-Variable aiSecret, aiKeyPointer
}
.\.venv\Scripts\python.exe -m uvicorn app.main:app --host 127.0.0.1 --port 8000
```

Ключ доступен процессу сервера через окружение, но его значение не появляется в команде, истории PowerShell или выводе. После остановки сервера можно удалить переменную текущего терминала: `Remove-Item Env:AI_API_KEY`. Для теста отключения задайте `$env:AI_ENABLED = 'false'` перед запуском.

## Формат и ошибки

LLM возвращает только объект `Analysis`: `summary`, `strengths`, `risks`, `tradeoff`, `reflection_question`, `limitations`. Фактические тезисы имеют `text` и `evidence_paths`. Ссылки — JSON Pointer относительно корня **SimulationResult**, например `/districts/4/after/S1`. Ссылка с `/simulation`, отсутствующее поле, отрицательный индекс или неверное экранирование отклоняются. Сервер проверяет лимиты каждого поля и общий предел 180 слов. Лишние поля запрещены.

HTTP 200 с `status=ok` содержит `analysis`, `unavailable_reason=null` и `message=""`. Ошибка AI для допустимого набора также возвращает HTTP 200, но с `status=unavailable`, `analysis=null` и безопасным русским сообщением. Версии, решения и оба Score сохраняются в обоих случаях.

| `unavailable_reason` | Что означает | Что проверить |
| --- | --- | --- |
| `disabled` | AI намеренно отключён | `AI_ENABLED` при запуске |
| `not_configured` | Нет ключа/модели или неверная конфигурация | Загрузку окружения, значения настроек и перезапуск |
| `timeout` | Истёк общий deadline | Доступность провайдера; число и Score уже доступны |
| `rate_limited` | Провайдер вернул HTTP 429 | Лимиты выданного доступа |
| `provider_error` | Ошибка сети, доступа или другая ошибка провайдера | Ключ, модель, поддерживаемый endpoint и адрес без вывода секретов |
| `invalid_response` | Обрезанный ответ, JSON/схема/длина/ссылки не прошли проверку | Совместимость модели и семантику её ответа; ошибку не заменяют mock-разбором |
| `refused` | Модель явно отказалась | Конкретную попытку; не выдавать отказ за учебный разбор |

Входные ошибки остаются 422 без Score. Непредвиденные ошибки математического ядра остаются 500; они не маскируются как недоступность AI. `/health` проверяет приложение и не подтверждает доступ к OpenAI.

## Проверки без платного API

```sh
.venv/bin/python -m pytest -q tests/test_ai.py tests/test_analyze_api.py
.venv/bin/python -m pytest -q
.venv/bin/python -m pip check
```

В PowerShell замените `.venv/bin/python` на `.\.venv\Scripts\python.exe`. AI-тесты подменяют HTTP-транспорт: реальные запросы и ключи для них не нужны. Они проверяют успешный ответ, ошибки и недоступность, строгую схему и ссылки, серверные метаданные, отсутствие AI-вызова для 422, общий deadline, один запрос без повторов, независимость других маршрутов и закрытие клиента.

Фактический полный прогон после уточнения промпта на macOS, CPython 3.14.4: **256 passed, 1 warning in 1.42s**. `pip check`: **No broken requirements found**. Это 130 сохранённых проверок backend и 126 новых проверок AI. Исходный прогон дал 131 passed; удалено только устаревшее ожидание 404 для `/api/analyze`, заменённое проверками реализованного маршрута. Предупреждение Starlette о переходе TestClient с `httpx` на `httpx2` не скрывается.

Браузерные проверки отдельно: `node tests/frontend.cjs` — **12 passed** с Playwright и Google Chrome. Для выбранного Chromium используйте `BROWSER_PATH`; при внешней установке Playwright — `NODE_PATH`. Подробности в [документации frontend](frontend.md#проверки). Все API в этих проверках подменены; они не заменяют живую приёмку.

Также выполнена проверка настоящего интерфейса с Uvicorn в браузере Codex, без `?demo=1` и подмены API. A показал Score **53,83**, стоимость **83** и две критические пары; B — **55,07**, стоимость **83** и одну пару. Для B подтверждены S1 Нуры **38 → 48** и сохраняющийся S2 **35**. Числа появились до настоящего AI-разбора. Ранее при `not_configured` AI-разбор не подменялся, рассчитанные числа оставались видны.

Финальная живая приёмка 23 сентября 2026 года: провайдер OpenAI, модель `gpt-4.1`, стандартный endpoint `/v1/responses`, общий deadline 12 секунд. Проверенные серверные ответы:

| Сценарий | HTTP / статус | Стоимость | `final_score` | Время `/api/analyze` |
| --- | --- | --- | --- | --- |
| A | 200 / `ok` | 83 | 53.825047500000004 | 3.5714735 с |
| B | 200 / `ok` | 83 | 55.0703475 | 2.620551875 с |

В A AI верно указал сохраняющиеся критические S1 и S2 Нуры. В B объяснил выход S1 Нуры из критической зоны и оставшийся дефицит S2. Ссылки прошли проверку существования; ключевые тезисы сопоставлены с расчётом вручную. Ограничение: ссылки на `changes` в `tradeoff` ответа B сами по себе не доказывают критичность; подтверждающие `before`/`after` присутствуют в соседних тезисах. Сервер не проверяет смысловую полноту доказательств. Это наблюдаемые задержки двух запросов, а не гарантия времени ответа провайдера.

Всего при приёмке выполнено **6 платных генераций**: четыре на `gpt-4.1-mini` выявили смысловые неточности при формально допустимом ответе. Промпт уточнили: запретили пересказ чисел и обобщения о целом районе по отдельным показателям, сузили тезисы и требования к подтверждающим ссылкам. Затем выполнены два финальных разбора A/B на `gpt-4.1`. Это отдельные ручные попытки после изменений; адаптер не повторяет запросы автоматически. Доступ к `gpt-4.1` дополнительно подтверждён через получение информации о модели (HTTP 200).

## Живая приёмка A/B

После настройки действующего ключа и доступной модели откройте `http://127.0.0.1:8000/` **без `?demo=1`**. Сделайте по одной попытке A и B; они вызывают платный API провайдера. Не запускайте одновременно те же запросы через curl, если уже проверяете их из интерфейса.

| Проверка | A | B |
| --- | --- | --- |
| M7 | Есиль | Нура |
| Стоимость | 83 | 83 |
| Score | 53.8250475 | 55.0703475 |
| S1 Нуры после мер | 38, критический | 48, выше порога |
| S2 Нуры после мер | 35, критический | 35, критический |

Числа должны появиться перед AI-разбором. Убедитесь, что AI для A не приписывает школе улучшение Нуры; для B объясняет устранение критического S1 и сохраняющийся дефицит S2. Модель получает одну попытку, поэтому не обязана сравнивать её с результатом A из предыдущего запроса. Переход между A и B обсуждает пользователь по видимым результатам. Никакой сценарий нельзя назвать доказанно оптимальным.

Для отдельной проверки HTTP после настройки можно вместо UI выполнить из bash/zsh:

```sh
curl --silent --show-error --max-time 20 --write-out '\nHTTP %{http_code}; seconds %{time_total}\n' \
  -H 'Content-Type: application/json' --data-binary @examples/scenario_a.json \
  http://127.0.0.1:8000/api/analyze
curl --silent --show-error --max-time 20 --write-out '\nHTTP %{http_code}; seconds %{time_total}\n' \
  -H 'Content-Type: application/json' --data-binary @examples/scenario_b.json \
  http://127.0.0.1:8000/api/analyze
```

Ключ находится только в окружении backend; в этих запросах его нет. Зафиксируйте модель, статус, задержку и проверку смысла каждого ответа без секретов. При отключении AI и повторном запуске интерфейс должен сохранить числа и явно показать недоступность текста. Деморежим и запись ответа допустимы как подписанный резерв; они не подтверждают работу живой интеграции.

Строгая схема и существующие ссылки не гарантируют правильную интерпретацию. A/B прошли живую проверку, но выборка мала; смысловое качество на широком наборе сценариев не оценивалось. После изменения модели или промпта повторите A/B и вручную проверьте ключевые выводы. Полное выступление с речью и хронометражем на 60 секунд ещё не отрепетировано. Публичный сервер, защита от расходования общего API-лимита и авторизация выходят за рамки этого локального MVP.
