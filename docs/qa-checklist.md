## 4. Подтверждённое расхождение QA-001

**MEDIUM — неверный пример границы бюджета в спецификации.** В [spec.md, разделе 8](spec.md#8-эталоны-и-критерии-готовности) набор M3 nura, M4 saryarka, M7 nura, M10 esil, M12 город указан как проверка ровно 100.

Воспроизведение по стоимости каталога:

```text
M3 + M4 + M7 + M10 + M12 = 30 + 15 + 24 + 12 + 14 = 95
```

Если использовать этот набор, поведение при бюджете ровно 100 останется непроверенным. Это ошибка документации, не подтверждённый дефект backend.

Корректный тестовый набор в [budget_exactly_100.json](../examples/budget_exactly_100.json):

```text
M3 nura + M6 город + M7 nura + M10 esil + M12 город
30 + 20 + 24 + 12 + 14 = 100
```

Категории представлены ровно по одному разу, конфликтов нет. Ожидается HTTP 200, total_cost=100, remaining_budget=0.

**Действие для владельца документации:** заменить только M4 saryarka на M6 город в соответствующем пункте spec.md. Спецификация, API-контракт, код и рабочие данные в этой QA-задаче не изменены. Других расхождений числовых таблиц с исходным документом при проверке не обнаружено; ошибок отсутствующего приложения установить нельзя.

Для каждого 422: ровно один элемент detail с полями code, message, path, context; сообщение непустое и понятное; поля Score отсутствуют. Проверять код, путь и заданный контекст, не полагаться на буквальное совпадение формулировки сообщения. Неожиданная ошибка сервера не должна маскироваться под ошибку пользовательского выбора.

Порядок валидации: формат/тип/лишние поля → количество → ID мер → повторы → районы → категории → несовместимости → бюджет. В тесте M1+M3 ожидается CATEGORY_COVERAGE, потому что эта стадия срабатывает раньше конфликта. Не менять это ожидание на INCOMPATIBLE_MEASURES ради удобства реализации.

## 7. AI — отдельный ожидающий этап

Включать эти проверки только после появления `app/ai.py` и маршрута `/api/analyze`. Моки подменяют границу вызова провайдера; не посылать реальные платные запросы и не использовать настоящие ключи.

| Подмена/вход | Ожидание |
| --- | --- |
| Любой невалидный набор | 422 до обращения к провайдеру; spy.call_count=0 |
| Корректный JSON Analysis | 200, status=ok, analysis валиден, числовые поля рассчитаны сервером |
| Отказ модели | 200, status=unavailable, unavailable_reason=refused, analysis=null |
| Timeout | 200, unavailable_reason=timeout; без скрытых повторов |
| Невалидный JSON | 200, unavailable_reason=invalid_response, analysis=null |
| Неверная схема или evidence_paths | То же invalid_response; не показывать непроверенный текст |
| Ошибка провайдера / rate limit | provider_error / rate_limited; безопасное сообщение, без ключей |

Для B baseline_score=52.55768 и final_score=55.0703475 сохраняются во всех корректно обработанных статусах unavailable. До и после отказа AI повторить /api/simulate(B) и сравнить результат. Отдельно в UI проверить сохранение показанных чисел; API-тест не доказывает работу frontend.

## 8. Следующая передача команде

1. Владелец документации исправляет QA-001, сохраняя каталог и стоимость мер.
2. Backend-разработчик публикует реализацию и сообщает commit для воспроизводимой проверки.
3. QA изучает новые тесты, добавляет недостающее и запускает TestClient/математические проверки без изменения приложения.
4. После AI-интеграции запускаются проверки с подменой провайдера. Живой AI и demo проверяются отдельно командой, не подменяются успешными mock-тестами.

На текущем этапе подтверждены согласованность QA-материалов и прохождение существующих браузерных тестов с mock API. Готовность backend, AI и полного MVP не подтверждена.
