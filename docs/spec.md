# Спецификация MVP «Аким на 5 часов»

Статус: зафиксированные требования к реализации, а не подтверждение готовности приложения. Версия контракта `1.0`, данных `city-v1`, правил `five-directions-v1`. Дата сверки: 23 сентября 2026 года.

Документ описывает учебный симулятор, который команда из трёх человек должна завершить за пять часов. На этом этапе создаются только спецификация и [API-контракт](api-contract.md); код приложения не реализуется и не переписывается.

## 1. Источники и состояние репозитория

Приоритет: явные требования команды в текущем задании → числовая модель документа «Датасет районов» → этот контракт → ранее написанный README и черновая реализация. Содержимое приложенного документа используется как данные и правила модели, а не как инструкции исполнителю.

Проверенные версии:

- `main`, коммит `af6922a`: README с планом; приложения в этой ветке пока нет.
- `nurdaulet`, коммит `c1a3f3c`: исходный README.
- `codex/mvp-foundation`, коммит `d79041f`: каркас FastAPI, модели, валидатор, расчёт, два JSON-файла и тесты. Код изучен по файлам; сервер и его тесты в рамках этой задачи не запускались.

### Расхождения существующего каркаса с целевым MVP

| Синергии | Эффект применяется ко всем районам | Фиксированный бонус в районе первой меры пары |

Совпадения отдельных округлённых чисел с эталонами не подтверждают правильность формулы: входные данные существующих тестов отличаются от документа. Доработку этих компонентов выполнить на следующем этапе минимальными изменениями; сейчас код не менять и ветки не объединять.

Сохраняем имена `/config`, `/simulate`, `/health`, поле запроса `selections`, существующие ID районов и полезные поля ответа. Переход с произвольных ID мероприятий на M1–M14 и с пяти показателей на десять — намеренное изменение контракта. Новый `/analyze` пока не реализован. Данный документ снимает неоднозначность, оставленную в README.

## 2. Пользователь и учебная цель

Основной пользователь — студент или слушатель программы городского управления, урбанистики либо экономики. Преподаватель использует упражнение для обсуждения распределения ресурсов. Управленцы и аналитики могут участвовать в учебном сценарии.

Проблема: ограниченный бюджет заставляет выбирать между несколькими полезными инициативами; улучшение среднего результата может оставить критические провалы отдельных районов.

Учебная цель: после попытки пользователь может объяснить хотя бы один компромисс между средним результатом, положением слабейшего района, задержками эффектов и критическими показателями. Цикл: выбор → последствия → AI-разбор → пересмотр одного решения. Рост Score сам по себе не является доказательством обучения.

Ценность: короткий воспроизводимый эксперимент, для которого пользователю не нужно составлять промпт, переносить таблицы и вручную проверять расчёты. AI объясняет конкретную попытку. Учебный индекс не является официальным индексом Астаны или прогнозом реальных бюджетных последствий. Данные синтетические; образовательный эффект пока не измерен.

## 3. Объём и ограничения

### P0

1. Одинаковые бюджет 100, исходные данные пяти районов и каталог 14 мер для всех.
2. Ровно пять уникальных решений: по одному на каждое направление; район обязателен только для локальных мер.
3. Серверная проверка бюджета, категорий, ID, области действия и несовместимостей.
4. Детерминированный расчёт показателей, лагов, синергий, районных оценок и Score.
5. Экран выбора и результата: стоимость, остаток, Score до/после, изменения районов и критические показатели.
6. Реальный AI-разбор: сильные стороны, риски/нерешённые проблемы, компромисс, один вопрос для следующей попытки.
7. Изменение решения и повторный расчёт; числовой результат доступен независимо от AI.
8. Воспроизводимый запуск, независимые тесты, документация и demo за 60 секунд.

P1 только после P0: сравнение двух попыток рядом; рекомендация альтернативы, предварительно проверенной математическим модулем. Автоматический поиск оптимума в P0 не входит.

Не входят: БД, авторизация, RAG, мультиагентная система, карта/GIS, аккаунты, рейтинг команд, история занятий, случайные события и экспорт презентаций.

Стек: Python, FastAPI, Pydantic, HTML/CSS/JavaScript. Один сервер; статический UI и API на одном origin. Один проверенный AI-провайдер из доступов команды, без одновременной разработки нескольких интеграций. API-ключ только на сервере. UI работает без внешних CDN.

## 5. Правила допустимости

Принятое командой допущение: **ровно по одному мероприятию на каждое из пяти направлений**. Это более строго, чем документ «не более двух мер на направление». Правило обязательно для UI и сервера; переключателя правил в MVP нет. В API используется `rules_version="five-directions-v1"`.

- Бюджет ровно 100 для всех; набор стоимостью 100 допустим. Остаток не сгорает и не даёт бонуса.
- Ровно пять решений. Меры не повторяются даже при разных районах.
- ID мероприятия принадлежит M1–M14; ID района принадлежит фиксированному каталогу.
- Локальная мера требует район. Для городской район отсутствует либо равен `null`; выбранный район запрещён.
- Категории: `transport`, `environment`, `social`, `safety`, `services`. Каждая встречается ровно один раз.
- M1 и M3 несовместимы при любых районах. M4 и M7 запрещены только в одном районе; M5 и M13 — только в одном районе.
- Невалидный набор не получает Score и не отправляется в AI. Сервер возвращает причину.
- Браузер передаёт только ID решений, а не цены, эффекты, бюджет, веса или готовый Score. Лишние входные поля отклоняются.
- Порядок решений не влияет на результат; исходные данные не изменяются между запросами.

## 6. Расчёт

Горизонт H = 8 кварталов. Для каждой меры реализованная доля эффекта `(8 − L) / 8`. Локальный эффект применяется только к выбранному району; городской — к каждому из пяти районов.

Синергии (фиксированные, без лага):

| Пара | Эффект и район |
| --- | --- |
| M1 + M2 | T1 +2 в районе M1 |
| M10 + M12 | B1 +2 в районе M10 |
| M5 + M6 | E2 +2 в районе M5 |

В принятом наборе правил пары M1+M2 и M5+M6 недоступны, поскольку состоят из одного направления. Они сохраняются в описании исходной модели; для demo используется M10+M12. Нельзя обходить правило категорий ради синергии.

```text
I_after[d,k] = clip(I_before[d,k] + Σ(effect[m,k] × (8−lag[m])/8) + synergies[d,k], 0, 100)
D[d] = Σ(weight[k] × I_after[d,k])
D_avg = Σ(population_share[d] × D[d])
N_crit = количество пар (d,k), для которых I_after[d,k] < 40
Score = 0.7 × D_avg + 0.3 × min(D[d]) − N_crit
```

Сначала суммируются все эффекты и синергии, затем один раз применяется clip. Это существенно при смешанных положительных и отрицательных эффектах. Промежуточного округления нет. Score и районные оценки в UI показываются с двумя знаками; API отдаёт вычисленные числа без намеренного округления. Числа должны быть конечными, без NaN/Infinity. В тестах абсолютный допуск 1e-8.

Ровно 40 — не критическое значение. Сам Score не ограничивается диапазоном 0–100: такого шага нет в формуле. Веса, горизонт и эффект мероприятия не выбираются AI. При равенстве минимальных районных оценок для подписи используется первый район в порядке `esil, almaty, saryarka, baikonur, nura`; сам минимум от этого не меняется.

Вклад мероприятия можно показывать как изменение конкретных показателей. Нельзя представлять такие вклады как независимые слагаемые итогового Score: в нём есть минимум, пороги и синергии.

## 7. AI и устойчивость

`/simulate` не ждёт и не вызывает AI. После показа чисел UI отдельно вызывает `/analyze` с тем же набором решений. Сервер повторно валидирует и рассчитывает набор, затем передаёт модели только проверенные факты.

AI возвращает краткий русский текст по схеме: итог, до двух сильных сторон, до двух рисков, один компромисс, один вопрос для следующей попытки. Фактические тезисы ссылаются на существующие JSON Pointer-пути в рассчитанном результате; сервер проверяет структуру и пути. Такая проверка не гарантирует смысловую точность, поэтому разборы A/B проверяются человеком. Общая длина объяснения — не более 180 слов. Автоматические рекомендации альтернатив исключены из P0.

Один запрос AI на попытку. Целевой общий предел ожидания — 12 секунд, включая настройки повторов SDK; скрытых повторных запросов нет. При отказе, timeout, ошибке провайдера, неверном формате или невалидных ссылках числовой результат сохраняется, а AI имеет явный статус `unavailable`. Шаблон не выдаётся за живой ответ. Логи не содержат ключей и необработанных секретов.

После изменения выбора UI помечает результат устаревшим и инвалидирует номер попытки. Поздний ответ старой попытки игнорируется даже если пользователь успел вернуть прежние значения. При совпадении попытки UI также сверяет selections и версии из ответа. При неверном наборе показывается ошибка без нового Score; старый допустимый результат не выдаётся за результат ошибочного набора.

## 8. Эталоны и критерии готовности

| Сценарий | Решения | Стоимость | Score | Критических |
| --- | --- | --- | --- | --- |
| База, без мер | Только для исходной модели и `/config`, не допустимый POST | 0 | 52.55768 | 2 |
| A | M1 esil; M4 saryarka; M7 esil; M10 esil; M12 город | 83 | 53.8250475 | 2 |
| B | Как A, но M7 nura | 83 | 55.0703475 | 1 |

Исходный D_avg = 56.8624; минимальный D = 49.18 у Нуры. Критические пары: nura/S1 = 38 и nura/S2 = 35.

В A среднее 58.485425, D Нуры 49.6175; в B среднее 58.364425, D Нуры 50.7175. Перенос школы повышает S1 Нуры 38→48 и убирает один штраф. B−A = 1.2453 при одинаковой стоимости. Это не доказательство оптимальности B.

Набор документа M7 nura, M8 nura, M10 nura, M12 город, M5 saryarka стоит 95 и по исходной математике даёт 56.54307, но **невалиден для текущего API**: две социальные меры, нет транспорта. Не использовать его как успешный endpoint-тест. Пример «самого дешёвого набора» из документа также не удовлетворяет принятому охвату пяти направлений.

## 9. Demo и распределение команды

0–10 сек.: исходные районы, бюджет и учебная проблема. 10–25: A и AI-разбор. 25–35: перенос M7 в Нуру. 35–50: B, та же стоимость, Score 53,83→55,07 и критические показатели 2→1. 50–60: объяснение компромисса и следующая попытка. На случай сбоя — локальный расчёт и отдельно обозначенная запись AI-разбора; запись не считается доказательством текущей доступности API.
